0. Basi Teoriche: Cos'è una VPN e IPsec?

Prima di entrare nei dettagli di FortiOS, è fondamentale avere chiari i concetti base:

La VPN (Virtual Private Network)

Immagina internet come un'autostrada pubblica. Se un'azienda a Milano vuole comunicare con la sua filiale a Roma, inviare i dati in chiaro è pericoloso. Una VPN è come un tunnel privato e blindato costruito sopra questa autostrada. Chi sta fuori dal tunnel vede il traffico, ma non può assolutamente vedere cosa c'è dentro. Le due sedi comunicano come se fossero collegate dallo stesso cavo locale.

IPsec (Internet Protocol Security)

IPsec è la tecnologia (l'insieme di protocolli) che materialmente costruisce e blinda questo tunnel. Garantisce tre elementi essenziali (la triade CIA):

  • Confidentiality (Riservatezza): I dati vengono crittografati (es. tramite AES). Se intercettati, sono illeggibili.
  • Integrity (Integrità): Usa funzioni di Hash (es. SHA) per applicare un "sigillo" ai dati, garantendo che nessuno li abbia manomessi durante il viaggio.
  • Authentication (Autenticazione): Garantisce che il router di Roma stia parlando davvero con il router di Milano (di solito tramite una password PSK o certificati).
Metafora della Negoziazione:
- Phase 1: Due spie si incontrano in un bar, si scambiano la parola d'ordine (PSK) e decidono in quale lingua in codice parlare. Creano un canale di controllo sicuro.
- Phase 2: Le spie iniziano a scambiarsi i veri documenti segreti (il traffico dati degli utenti) usando la lingua in codice appena concordata.

1. Architettura IPsec: Route-Based è il Re

Per l'esame NSE 4, devi ricordare che FortiGate supporta due tipi di VPN, ma una è lo standard assoluto:

  • Route-Based VPN (Raccomandato): FortiOS crea automaticamente un'interfaccia virtuale (Tunnel Interface) quando crei la Phase 1. Il routing (Static Routes o protocolli dinamici) decide quale traffico entra nel tunnel. Le Firewall Policy usano questa interfaccia. Molto più flessibile (supporta SD-WAN, OSPF, ecc.).
  • Policy-Based VPN (Legacy): Nessuna interfaccia virtuale. Il traffico viene crittografato se fa match su una Firewall Policy con azione "IPsec". Sconsigliata e limitata.
Da ricordare: In una Route-Based VPN, hai bisogno di due firewall policy per permettere il traffico bidirezionale (una in entrata e una in uscita), oltre alla rotta statica che punta alla tunnel interface.

2. Negoziazione: Phase 1 (IKE) e Phase 2 (IPsec)

Phase 1 (IKE) - Autenticazione e Canale Sicuro

  • Main Mode vs Aggressive Mode: Main Mode = 6 messaggi, ID protetto. Aggressive Mode = 3 messaggi, ID in chiaro (spesso usato per Dial-Up/Remote access con IP dinamici in IKEv1).
  • NAT Traversal (NAT-T): Necessario se c'è un NAT lungo il percorso. Sposta il traffico da ESP (Protocollo 50) a UDP 4500. FortiGate lo rileva automaticamente durante la negoziazione.
  • DPD (Dead Peer Detection): Meccanismo di keepalive. Se il peer non risponde, la Phase 1 viene abbattuta e il routing si aggiorna (fondamentale per le VPN ridondanti).

Phase 2 (IPsec) - Tunnel Dati

  • Quick Mode Selectors: Definiscono quali subnet possono parlarsi. Nelle Route-Based, la best practice è lasciarle a 0.0.0.0/0 e delegare il controllo al Routing e alle Firewall Policy.
  • PFS (Perfect Forward Secrecy): Costringe a generare nuove chiavi Diffie-Hellman per la Phase 2. Se abilitato su un peer, deve essere abilitato e coincidere anche sull'altro.

3. Routing Avanzato e VPN Ridondanti (Focus Esame)

Spesso all'esame ti chiederanno cosa succede se hai due tunnel VPN verso la stessa destinazione.

  • Failover (Attivo/Passivo): Si usano due rotte statiche con la stessa destinazione ma Distance diversa. La rotta con Distance minore è attiva. Se il tunnel cade, subentra l'altra.
  • Load Balancing (Attivo/Attivo): Entrambe le rotte hanno la stessa Distance. Il traffico viene bilanciato. Si può usare l'ECMP o l'SD-WAN per gestire il bilanciamento.
  • Overlapping Subnets: Se la LAN locale e remota usano lo stesso spazio IP, si deve applicare il NAT all'interno della VPN. Si usano Virtual IPs (VIP) in entrata e IP Pools in uscita per mascherare le reti.

4. Troubleshooting CLI (Il Pane Quotidiano)

Se la VPN non sale, questi sono i comandi essenziali:

# Controlla lo stato generale dei tunnel (se la rotta non c'è, il tunnel potrebbe non salire)
get vpn ipsec tunnel summary

# Il debug IKE è la risposta a quasi tutte le domande di troubleshooting VPN all'esame
diagnose vpn ike log-filter dst-addr4 x.x.x.x
diagnose debug application ike -1
diagnose debug enable
Errori Comuni:
- pre-shared key mismatch: La password PSK è sbagliata.
- proposal mismatch: Gli algoritmi di cifratura/hash (es. AES/SHA) non coincidono tra i due peer.
- no matching gateway: L'IP remoto non è corretto o l'IKE ID non corrisponde.

5. Auto-Verifica Rapida (Q&A) prima dell'Esercitazione

Clicca sulle domande per vedere le risposte e verificare di aver compreso tutto.

Qual è il protocollo usato se il NAT-T è attivo?

UDP sulla porta 4500. Senza NAT-T, verrebbe usato il protocollo ESP (IP Protocol 50) e UDP 500 per IKE.

In una Route-based VPN, di quante policy hai bisogno minimo per far parlare due LAN?

Due. Una per il traffico dalla LAN al Tunnel, e una per il traffico dal Tunnel alla LAN.

Se vedi l'errore "proposal mismatch" nel debug, cosa controlli?

Devo controllare che Fase 1 e Fase 2 abbiano gli stessi algoritmi di Encryption (es. AES-256) e Authentication (es. SHA-256) configurati su entrambi i firewall, e lo stesso gruppo Diffie-Hellman.

A cosa serve il PFS (Perfect Forward Secrecy)?

Forza la generazione di un nuovo set di chiavi (scambio Diffie-Hellman) dedicato per la Fase 2, anziché derivarle dalla Fase 1, aumentando la sicurezza.

6. Lab Pratico: Route-Based IPsec VPN (Step-by-Step)

Scenario: Dobbiamo collegare la sede di Milano (HQ) con quella di Roma (Branch) usando una Route-Based VPN. Questo è l'approccio standard raccomandato da Fortinet.

  • HQ (Milano): IP Pubblico WAN: 203.0.113.1 | Rete LAN: 10.0.1.0/24
  • Branch (Roma): IP Pubblico WAN: 198.51.100.1 | Rete LAN: 10.0.2.0/24
  • PSK: FortiSecret123!

Step 1: Creazione della Phase 1 (su HQ Milano)

Prima creiamo il canale di controllo verso Roma.

# Dalla CLI di HQ (Milano)
config vpn ipsec phase1-interface
edit "VPN-to-Roma"
set interface "wan1"
set peertype any
set net-device disable
set proposal aes256-sha256
set remote-gw 198.51.100.1 # Punta all'IP WAN di Roma
set psksecret FortiSecret123!
next
end

Step 2: Creazione della Phase 2 (su HQ Milano)

Leghiamo il tunnel dati alla Fase 1. Lasciamo le subnet a "tutte" (0.0.0.0/0) delegando il controllo al routing.

config vpn ipsec phase2-interface
edit "VPN-to-Roma-P2"
set phase1name "VPN-to-Roma"
set proposal aes256-sha256
# src-subnet e dst-subnet rimangono a 0.0.0.0/0 (default)
next
end

Step 3: Routing Statico (su HQ Milano)

Diciamo al firewall di Milano: "Se devi inviare dati alla LAN di Roma (10.0.2.0/24), buttali dentro l'interfaccia VPN".

config router static
edit 0
set dst 10.0.2.0 255.255.255.0
set device "VPN-to-Roma"
next
end

Step 4: Firewall Policy Bidirezionali (su HQ Milano)

Senza policy il traffico viene droppato. In una VPN Site-to-Site classica, il NAT deve essere spento sulla policy.

config firewall policy
# Policy 1: Da Milano verso Roma (Outbound)
edit 0
set name "Milano_to_Roma"
set srcintf "lan"
set dstintf "VPN-to-Roma"
set srcaddr "all"
set dstaddr "all"
set action accept
set schedule "always"
set service "ALL"
set nat disable # Fondamentale!
next

# Policy 2: Da Roma verso Milano (Inbound)
edit 0
set name "Roma_to_Milano"
set srcintf "VPN-to-Roma"
set dstintf "lan"
set srcaddr "all"
set dstaddr "all"
set action accept
set schedule "always"
set service "ALL"
set nat disable
next
end
Step 5: Configurare Branch (Roma) in modo speculare
Ora ripeti gli stessi passaggi sul firewall di Roma. Inverti gli IP e le interfacce:
- Fase 1: remote-gw diventa l'IP WAN di Milano (203.0.113.1).
- Rotta statica: La destinazione diventa la LAN di Milano (10.0.1.0/24).
- Policy: Da LAN Roma a VPN, e da VPN a LAN Roma.

Step 6: Attivazione e Verifica

I tunnel in FortiOS non si alzano da soli (a meno di non attivare auto-negotiate). Si alzano quando arriva il primo pacchetto utile.

# Esegui dal PC nella LAN di Milano verso un PC nella LAN di Roma:
ping 10.0.2.10

# Oppure forzalo dal FortiGate:
diagnose vpn tunnel up VPN-to-Roma
